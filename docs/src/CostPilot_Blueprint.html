1Purpose and scope

CostPilot already has three documents that establish intent. The White Paper argues why management accounting is the unattended territory and what the product is. The Phase 1 Plan defines modules, milestones, and success criteria. The Phase 2 Plan adds activity-based costing, budgeting, performance measurement, connectors, and monitoring. This blueprint is the fourth document: it translates those documents into the contracts an engineering team can build against.

It is deliberately opinionated. Where the phase plans leave a technical choice open, this document names a default, records the trade-off, and assigns the decision an owner. That is not an attempt to freeze the product. It is an attempt to freeze the parts that become expensive to change after the first pilot: the data model, the boundary between model and engine, the audit trace, and the rulebook.

1.1 What “blueprint” means here

Not a UI specification and not a sprint plan. The blueprint covers the structural layer:

  • Contracts between the user interface, the planner model, the tool registry, the calculation engine, and the audit service.
  • Schemas for the cost data layer, the rulebook, the calculation trace, and the API payloads.
  • Policy for sign conventions, rounding, units, missing data, capacity assumptions, and refusal behaviour.
  • Gates that decide when a milestone is actually complete and when an answer is allowed to reach a user.

Interface copy, chart styling, onboarding, and the precise wording of prompts will change weekly. The decisions here should not.

1.2 Phase 1 is done when

A cost analyst can load one month of GL actuals, standard costs, budgets, and volumes for a three-product, two-plant manufacturer; ask a variance question or one of seven short-run decision questions; and receive an answer whose every figure is computed by the engine, traceable to source records and rule IDs, and re-performable by a controller. The same question against the same snapshot returns the same numbers, byte for byte. The working paper exports to Excel without a parallel spreadsheet.

That statement is narrower than the product vision and broader than a demo. It requires the data layer, the variance engine, the decision engine, the planner, the audit surface, and the export path to work together on one realistic dataset. It does not require ABC, ERP connectors, or multi-entity consolidation.

1.3 Build order

The dependency chain is strict. Data and formulas come first because every later module consumes their contracts. The variance explainer comes next because it exercises the full trace and narration path on a familiar finance output. The decision engine follows, because its outputs are the sales demo and because it stress-tests assumption handling. The conversational shell comes last, not because it is unimportant but because a planner without trustworthy tools is a demo, not a product.

M0  contracts, trace, decimal arithmetic, golden harness
 └─ M1  cost data layer + variance formulas
     ├─ M2  variance & flux explainer + raw audit panel
     │   └─ M4  chat shell, planner, confirmation, RBAC
     └─ M3  short-run decision engine
         └─ M5  pilot hardening, live close pack

Phase 2 follows the same pattern: connector foundation first, because ABC driver data, alerting, and scorecard KPIs all depend on richer ingestion; ABC second, because it is the strongest value demonstration; then monitoring, budgeting, performance, and group reporting. Section 11 gives the full sequence with exit gates.

1.4 Deliberate non-goals

Phase 1 is not a general ledger, an ERP, a report writer, a forecasting system, or a general-purpose finance chatbot. It does not write back to any system. It does not support multi-currency translation, intercompany elimination, or ABC. It does not infer account classifications silently and it does not answer a question whose data is missing by estimating a plausible number. Section 12.3 restates these as a scope contract that change control must explicitly reopen.

3System architecture

The runtime is a deterministic orchestrator around a language model, not an autonomous agent around a database. The distinction matters. The model proposes a plan; the orchestrator decides whether the plan is admissible, what it is allowed to touch, and when the result is fit to show. The engine computes; the renderer formats; the audit service records. No component is trusted to do another’s job.

3.3 Request lifecycle

  1. Receive. The API authenticates the user, resolves tenant and row scope, and appends the message to the session.
  2. Ground. The orchestrator builds a planner context: a capability card (datasets, periods, dimensions, supported analyses, data-quality status), a conversation summary, and references to prior run IDs. No raw ledger rows.
  3. Plan. The planner returns a plan JSON: intent, tool, arguments, assumptions, missing fields, and at most one clarification question.
  4. Admit. The orchestrator validates the plan against the tool schema and policy. Unknown tools, out-of-scope dimensions, arithmetic fields, or unregistered decision types are rejected.
  5. Confirm. If any argument is inferred, defaulted, or policy-bearing, the user sees a parameter sheet with value, source, and edit control. Execution waits. Edits create a new plan version.
  6. Pin. The orchestrator creates a run and pins the snapshot, registry, engine, rulebook, prompt, and model versions. The input hash is computed.
  7. Execute. The execution service resolves dimensions, compiles scoped SQL, and calls the engine. Heavy scans run against pre-aggregated marts where possible.
  8. Compute. The engine returns a CalcResult with steps, facts, assumptions, warnings, and source references. No prose yet.
  9. Validate. Schema, identity, unit, coverage, basis, and provenance checks run. A blocking failure stops the run with a remediation card.
  10. Render. The renderer selects the verdict template from the engine’s decision output, requests a rationale from the model using fact slots only, validates the rationale, and substitutes formatted values.
  11. Seal. The audit record is hashed and appended. The response streams to the client with the run ID.
  12. Follow up. The card offers export, re-performance, a trace view, and suggested next questions generated from the capability card, not from the model’s imagination.

No answer exists before step 9 passes. Partial results, “rough” numbers, and provisional narratives are not sent. A failed validation produces an error card with the checked facts and a path forward, never a softened answer.

3.4 Two interaction lanes, one contract

Question lane

Free-text or voice-transcribed question. The planner selects a tool and extracts parameters. Best for experienced analysts who know what they want and for follow-ups such as “now assume the idle capacity is only 1,000 units.”

Workflow lane

A guided form generated from the same tool JSON Schema. Required fields, enums, units, and confirmation are identical. Best for non-accountants, for auditability, and as the fallback when the model is unavailable.

The lanes must not diverge. Tool schemas are the single source of truth for fields, validation, and confirmation. The form renderer generates controls from schema annotations (title, description, examples, x-unit, x-confirm). A new workflow is added once, in the registry, and appears in both lanes.

3.6 Centralized versus pluggable

Three things stay centralized because fragmentation would break trust: the rule registry (one formula set, one sign convention), the trace format (one audit schema), and the validator (one definition of shippable). Three things are pluggable because Phase 2 and customer environments demand it: data connectors, cost models (traditional versus ABC/TDABC), and renderers (chat card, Excel, PDF). A connector may not introduce a new fact shape without a schema migration; a cost model may not bypass the rule registry.

4The LLM contract

The planner is the only non-deterministic component in the answer path. It is therefore treated as an untrusted proposals engine: useful for language, inadmissible as an authority. The contract below is enforced by schemas and the orchestrator, not by prompt wording alone. A model that ignores the prompt should fail validation, not produce a plausible wrong answer.

4.5 Confirmation protocol

Confirmation is the moment the product earns or loses trust. The user must see what the system believes before it calculates, especially when the belief came from implication rather than explicit statement.

  • Every argument has a source: user_explicit, user_implied, registry, lookup, policy_default, or engine_default.
  • Confirmation is mandatory for user_implied, policy_default, and any registry or lookup value that changes a policy: capacity state, avoidable versus unavoidable cost, costing basis, allocation method, materiality threshold, or a what-if operator.
  • The parameter sheet shows the argument label, resolved dimension name, value with unit, source badge, and an edit control. It also shows the fields the plan did not use, so the user can catch a missing driver.
  • Edits create a plan version. The run pins the version; the audit record stores the diff between the model’s proposal and the user’s confirmed values.
  • Capacity conflicts are surfaced, not resolved. If the user says “idle capacity” but the snapshot shows utilization above 95% for the period, the sheet warns with the utilization figure and requires an explicit override reason. The engine never silently substitutes an opportunity cost.
  • Auto-execution is narrow. Only plans with all-explicit arguments, no policy-bearing fields, and complete data may run without a confirmation step. Even then, the analysis card repeats the parameter summary.

Do not let the model state a recommendation before confirmation. “It looks profitable” in the planning turn is a verdict without a calculation. The planner is instructed to describe the proposed analysis, not its outcome. The UI renders the plan as “I will compare X against Y using Z assumptions”, never as a conclusion.

4.6 Narration: slots, not sentences with numbers

The White Paper’s rule is that the model narrates results. The implementation makes that literal. The response has three blocks, and only the middle one involves the model:

  1. Verdict block — deterministic. The engine returns a decision enum (accept, reject, investigate, favorable, adverse, mixed). The renderer selects a fixed sentence template. The model cannot change it.
  2. Rationale block — model, slot-only. The model writes two to four sentences using placeholders such as {{f1|INR}}. It receives the fact table but is forbidden from restating a value manually.
  3. Evidence block — deterministic. Tables, waterfall, assumptions, source links, step list, and export. Always present, always formatted by code.
Accepting the order adds {{f1|INR}} of incremental profit. The floor price is
{{f2|INR}} per unit, and the offer leaves {{f3|INR}} per unit of headroom.
The conclusion holds only while the capacity assumption is confirmed; if it changes, rerun the analysis.

The renderer receives a fact table like this one and substitutes only the referenced values:

Allowed placeholder grammar

{{fact_id|format}} only. Formats are a fixed allowlist: INR, INR0, PCT1, PCT2, QTY0, QTY2, RATIO2, HOURS1. Formatting is locale-aware and configured per tenant; Indian digit grouping is used for INR by default, international grouping otherwise. No arithmetic is permitted inside a placeholder. 4.8 Prompt and model governance

  • Prompts live in the repository as versioned files. Their hash is stored in every run. A prompt change requires the planner eval subset to pass and a domain review.
  • Model ID, provider, temperature (0), top-p (1), and token limits are pinned per run. A fallback model is allowed only if it passes the same eval suite; the fallback is recorded.
  • No customer data appears in prompt templates or few-shot examples. Examples use synthetic accounts and amounts.
  • Tool descriptions are treated as code: reviewed, tested for ambiguity, and versioned with the tool.
  • A red-team suite runs on every prompt or model change: instruction override, invented account, “just estimate it”, arithmetic request, unit conversion, and a ledger row containing an instruction.

5Cost data layer

The data layer is where projects of this kind fail. The intelligence is worthless on untagged data, so the registry and the gates are the first deliverable, not an afterthought. Two rules govern the design: every fact is dimensional and every classification is versioned. A third rule governs behaviour: the system would rather refuse an analysis than silently infer a fixed/variable split.

5.1 Principles

  • Registry first. No analysis runs against an account whose behaviour and direct/indirect status are unknown, unless the analysis does not depend on that classification and the omission is disclosed.
  • One canonical fact shape. Amounts, quantities, prices, hours, and volumes are separate typed facts, not strings in a spreadsheet column.
  • Immutable snapshots. Ingestion creates a new snapshot; it never edits a prior one. Runs pin a snapshot.
  • No silent coercion. Unparseable rows fail the load with row-level errors. Unknown dimension members go to a mapping queue.
  • Weighted quality. Coverage is measured by cost amount, not by account count. A single untagged account holding 8% of cost is a blocking problem even if 98% of accounts are tagged.

5.4 Account registry

The registry is a versioned classification of every account, with optional plant-level overrides. It answers four questions the engine cannot proceed without: is the account fixed, variable, or semi-variable; is it direct or indirect; is it controllable by the manager being evaluated; and is it manufacturing or period cost.

Relationship to standard cost cards. The registry classifies GL accounts and period costs. Standard cost cards carry the per-unit material, labour, and overhead standards used for product costing and standard-cost variances. The engine must not add both: product-level variable cost comes from the standard cost card; period fixed cost comes from the registry and GL. Where a card is missing, the engine blocks the product-level analysis and names the missing card; it does not fall back to account averages.

Registry lifecycle

  1. Import the chart of accounts with statement, type, and cost-center mapping.
  2. Suggest behaviour and direct/indirect using deterministic rules first (account type, name patterns, standard-cost mapping), then a model suggestion as a secondary hint.
  3. Review in a bulk grid sorted by amount, so the analyst spends time on material accounts. Every suggestion shows its evidence.
  4. Approve with a named approver and timestamp. Approval is per version, not per row.
  5. Version any change as a new registry version with a diff and reason. Runs pin the version they used.

Weighted coverage is computed as tagged cost amount divided by total cost amount for the analysis scope. The pilot target is 99.9% or better; below 99% is blocking, and any single untagged account above 2% of scope is blocking regardless of the total.

5.5 Ingestion pipeline

  1. Receive. Upload or connector extract; allowlist XLSX and CSV; 100 MB per file; macro-free; virus scan; zip-bomb protection.
  2. Stage. Load raw values as strings into staging tables with file, sheet, row, and column references.
  3. Map. Resolve columns to the canonical template; unresolved required columns fail the load with a mapping error.
  4. Type. Parse amounts, quantities, prices, hours, dates, and periods with explicit formats. No locale guessing beyond the declared tenant locale.
  5. Resolve. Match dimension members exactly; unknowns go to a mapping queue and the load reports them.
  6. Validate registry. Every cost account in scope must have a behaviour and direct/indirect tag, or an approved override.
  7. Run gates. G1–G12 below. Blocking failures stop the canonical load.
  8. Reconcile. Compare loaded totals to uploaded control totals and to the prior period where applicable.
  9. Load canonically. Write typed facts in one transaction per load.
  10. Freeze. Build Parquet files, compute hashes, write the manifest, and register the snapshot.
  11. Report. Show a quality report with pass/warn/block per gate, affected amounts, and remediation links.

6Deterministic engine

The engine is the authority. It is a library of pure functions with no database access, no network calls, and no model calls. It receives typed inputs, applies a registered rule, and returns a value plus the exact steps that produced it. If the engine cannot compute something under the stated policy, it raises a domain error with a remediation code. It never fills a gap with an estimate.

6.3 Numeric, unit, and rounding policy

  • Decimal only. Construct from strings. Floats are banned in the engine package by lint. Division uses an explicit context with at least 28 digits.
  • No rounding mid-calculation. Steps carry full precision. Rounding happens once, at rendering: currency 2 decimals, rates 4, quantities 4, percentages 2. A displayed total may differ from the sum of displayed components by ₹0.01; the trace shows a rounding-adjustment line and the full-precision values.
  • Units are dimensional. Amounts are currency; quantities are UOM; rates are currency per UOM. The engine refuses to add incompatible units. Conversions happen only through the explicit UOM registry, never implicitly.
  • Currency is per entity. Phase 1 rejects mixed-currency scopes. There is no FX translation and no display-currency conversion.
  • Sign convention. Internally, a variance is positive when favorable. API results carry a signed value and a favorable boolean. The UI prints the magnitude with an F/A label, never a negative number for a variance. Actual losses use parentheses.
  • Deterministic order. Steps are ordered by dependency, then by rule ID. No unordered iteration or locale-dependent sorting affects numbers.

6.8 Phase 2 formulas

ABC and TDABC

Pool rate = total pool cost ÷ total driver quantity. Allocated cost = pool rate × driver quantity consumed. TDABC capacity cost rate = cost of capacity supplied ÷ practical capacity; cost per transaction = rate × time per transaction; unused capacity cost = rate × (capacity − time used). Allocations must sum to the pool total within ₹0.01; unused capacity is shown as a separate line, never spread silently into products.

Example: a setup pool of ₹600,000 with 1,500 setups gives ₹400 per setup. A high-volume product consuming 200 setups receives ₹80,000; a low-volume custom product consuming 1,300 receives ₹520,000. A traditional machine-hour allocation that gives the high-volume product 80% of the pool would assign ₹480,000 and ₹120,000 — reversing the economics. The report always shows traditional and ABC side by side; the difference is the finding, not a hidden adjustment.

Budget chain

Production units = sales units + desired ending finished goods − beginning finished goods. Material purchases = production usage + desired ending raw material − beginning raw material. Labour hours = production units × standard hours per unit. Each node is a pure function with a versioned output; a scenario is an overlay diff, not a copied workbook. Example: sales 10,000 + ending 1,200 − beginning 1,000 = 10,200 units produced; at 2 kg per unit, usage is 20,400 kg; with ending 1,500 and beginning 1,200, purchases are 20,700 kg.

Performance measurement

ROI = operating income ÷ average operating assets; residual income = operating income − required return × average operating assets. Example: operating income ₹1,200,000 on assets ₹6,000,000 is 20% ROI. A new investment adds ₹180,000 of income on ₹1,200,000 of assets — 15%, above the 12% required return but below the division’s current 20%. The manager rejects it under ROI; residual income rises by ₹36,000. The engine shows both views on the same data and labels the conflict explicitly, without declaring which manager behaviour is “right”.

7.3 Hash chain and immutability

  • Events are canonicalized as JSON with sorted keys, no insignificant whitespace, UTF-8, and decimals as strings.
  • event_hash = SHA256(previous_hash || canonical_json(event)). The run seal stores the final hash. Any later mutation breaks the chain.
  • Audit rows are append-only in Postgres; a trigger rejects updates and deletes. Sealed run exports are written to object storage with object lock.
  • A verification endpoint recomputes the chain for a run or a date range and reports the first broken link.
  • Retention: audit metadata and traces for seven years; raw snapshots for thirteen months in the pilot, configurable per contract. Deleting a snapshot does not delete its audit metadata.

7.4 Re-performance

Re-performance is the operational definition of trust. The user opens a run, selects “Re-perform”, and the system re-executes the pinned tool against the pinned snapshot with the confirmed arguments. Every step value is compared to the stored value. The result is one of three states: exact match, display-rounding difference (documented, within the display tolerance), or mismatch (a defect, with the differing steps shown).

  • The engine wheel and container image for each released version are retained so a re-performance uses the same code, not today’s code.
  • The comparison is numeric only. Prose may differ because a model version changed; that is not a numerical mismatch.
  • A command-line re-performance tool supports sampled audits: costpilot reperform --run run_01J9ZK4T7Q --json.
  • Every completed run is sampled for nightly re-performance. A mismatch rate above zero is a release-blocking incident.

8.5 Exports

The export is a copy of a validated run, not a fresh calculation. It carries the run ID, snapshot ID, engine and rulebook versions, and the validation summary on every sheet or page.

  • XLSX: tabs for Summary, Analysis, Trace, Assumptions, Sources, and Data Quality. Numbers are stored as numbers with explicit formats, not strings. Freeze panes and column widths are set. No macros.
  • Formula-injection protection: any text cell beginning with =, +, -, @, tab, or carriage return is prefixed with an apostrophe. This applies to account names, product names, and every imported string.
  • PDF: server-rendered from the same structured payload as the card, not a screenshot. Page footer includes run ID and “Draft” status until the run is sealed.
  • JSON: the full trace schema for audit tooling and re-performance.

9.3 Coding standards

  • Engine purity. No I/O, no database, no model, no clock, no random. Inputs and outputs are frozen dataclasses. Every rule has a docstring with its rule ID, source citation, and a worked example.
  • No floats. A lint rule bans float in engine code. Decimal is constructed from strings. Division contexts are explicit.
  • Typed boundaries. mypy --strict on contracts, engine, planner, and renderer. The API may use narrower typing at the framework edge only.
  • SQL discipline. Parameterized queries only; no string interpolation of user values. Query compiler owns scope predicates. Every analytical query is reviewed and has a test fixture.
  • Errors are typed. Domain exceptions carry a code and remediation. No bare Exception reaches the API boundary.
  • Logs exclude amounts by default. Log IDs, hashes, stages, durations, and gate results. Amounts are available in the trace to authorized users, not in application logs.
  • Version everything that changes an answer: engine, rulebook, registry, tool, prompt, contract schema, snapshot transform. Versions are semantic and stored in the run.
  • ADRs for structural changes. Data model, trust boundary, tool contract, and trace schema changes require a short architecture decision record.

10.3 Property and metamorphic tests

  • Scaling all volumes and variable costs by k scales contribution by k and leaves fixed cost unchanged.
  • A change in actual price moves MPV and leaves MUV unchanged when quantity is held constant.
  • A change in actual quantity moves MUV and leaves MPV unchanged when price is held constant.
  • At the computed floor price, incremental profit is exactly zero.
  • At the shutdown indifference point, operate and shut down profit are equal.
  • When actual volume equals budget volume, the flexible budget equals the static budget and the volume variance is zero.
  • Reallocating an ABC pool across drivers preserves the total allocated plus unused capacity.
  • For any inventory increase, absorption income minus variable income equals change in units × fixed overhead rate.
  • Rounding the display never changes the stored step value or the re-performance result.

Extension points designed now, not later. The tool registry is versioned so Phase 2 tools can be added without breaking the planner. The snapshot schema is additive, with driver events as new facts rather than a parallel store. The executor treats a monitor run exactly like a user run, with origin=monitor, so alerts inherit the same trace and validation. The connector interface is defined as discover, extract, control-totals, and map, with human approval on mappings. Budget versions and scenario overlays are new tables keyed by the same period and account dimensions. No Phase 1 module may assume a single product, plant, or period in a way that blocks multi-entity reporting.

11.5 Change control

Four artifacts are under change control: the tool contract, the trace schema, the data schema, and the rulebook. A change to any of them requires an ADR, a version bump, a migration plan, and the relevant eval or golden suite. Prompt changes require the planner eval subset. A change to the scope contract in Section 12.3 requires explicit product-owner and engineering-lead approval; it is not a backlog decision.

12.4 Release definition of done

  • Performance budgets met on the one-million-row fixture.
  • Security scan clean of high and critical findings; export injection test passes.

F. Pilot data-readiness checklist

  • Twelve months of GL actuals at account × plant × cost-center grain, with a control-total reconciliation per period.
  • Chart of accounts with statement, type, and a named owner for classification decisions.
  • Standard cost cards covering at least 90% of product cost, with material, labour, variable overhead, and fixed overhead components.
  • Standard usage per product: material quantity, labour hours, machine hours, and UOM.
  • Actual quantities, prices, hours, and rates, or a subledger extract from which they can be produced.
  • Production, sales, and inventory movement by product and plant.
  • Budget by account and period, with the version that was in force during the close.
  • Capacity and utilization evidence for the plants in scope, sufficient to test an idle-capacity claim.
  • For Phase 2: setup, inspection, purchase-order, and order-line event logs for at least one plant.
  • A named data owner, a cost-accounting reviewer, a security review contact, and a pilot close date.
